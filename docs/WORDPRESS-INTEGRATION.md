# ArcticRC — WordPress integration

## Источники

- Репозиторий темы: `AndrewStartcev/arcticrc-wp`
- Старый сайт: https://arcticrc.ru/
- Figma: файл `RMPKvvfrl93N29fiGoX1qA`, стартовый node `20:12`
- Архитектурные референсы: `argokov.ru-wp`, `RoverLand-wp`

## Исходное состояние

В репозитории уже есть готовая BEM-верстка и ассеты:

- `html/index.html`
- `html/services.html`
- `html/services-soil-testing.html`
- `html/equipment-sale.html`
- `html/equipment-rent.html`
- `html/contacts.html`
- `assets/css/**`
- `assets/js/**`
- `assets/fonts/**`
- `assets/media/**`

Главное правило: WordPress интегрируем поверх существующей верстки. Классы и frontend-логику без причины не переписываем.

## Стек

- WordPress, classic custom theme
- ACF Pro + Local JSON
- Rank Math SEO
- PHP-шаблоны и существующий JS
- без Elementor / WPBakery / визуальных конструкторов

Кеш и SMTP добавляем только после понимания окружения и необходимости.

## Порядок согласования

После каждого законченного этапа я указываю его ID, например: **AR-003 готов к проверке**.

После проверки Андрей может дать один из ответов:
- **«AR-003 согласовано»** — фиксируем статус **Согласовано**;
- **«AR-003 правки: …»** — фиксируем **Нужна правка** и список замечаний;
- **«AR-003 пока не проверял»** — оставляем **Готово к проверке**.

Следующий крупный шаблон начинаем после того, как предыдущий доведён хотя бы до состояния **Готово к проверке**. Так прогресс всегда виден по таблице и ни одна часть проекта не теряется.


## Архитектура контента

### Услуги

CPT `service` + taxonomy `service_direction`.

Целевой URL:

`/services/{direction}/{service}/`

Так структура остается масштабируемой и не требует отдельных PHP-файлов под каждую услугу.

### Проекты

CPT `project`.

План полей:
- заголовок;
- превью;
- регион/город;
- связанная услуга;
- краткое описание;
- основной контент;
- галерея;
- связанные услуги.

### Оборудование

Один CPT `equipment`.

Аренда/продажа — taxonomy `equipment_mode` или соответствующее ACF-поле. Один объект не нужно дублировать, если он доступен сразу в двух режимах.

## Ассеты

CSS и JS на первом этапе не пересобираем.

Все существующие файлы подключаются через `wp_enqueue_style()` / `wp_enqueue_script()`, версии — через `filemtime()`.

При переносе HTML:
- относительные пути к media заменяем на theme URI;
- внутренние HTML-ссылки заменяем на WordPress permalinks;
- статические `title`/meta убираем, SEO отдаем WordPress + Rank Math.

## Header / Footer

Сохраняем текущую разметку.

Динамические данные:
- WP menus;
- телефон/email;
- социальные ссылки;
- реквизиты;
- юридические ссылки;
- текущий год.

## Формы

В верстке уже есть собственная форма и JS.

Целевой вариант:
- сохранить HTML/BEM формы;
- backend обработчик WordPress;
- nonce;
- серверная валидация;
- антиспам;
- уведомление на email;
- согласие с ПДн;
- CRM-интеграция при необходимости.

Не заменять форму тяжелым конструктором только ради отправки.

## SEO и миграция

До релиза обязательно:
1. получить полный список URL старого сайта;
2. определить новый URL каждого документа;
3. сохранить URL где возможно;
4. для измененных адресов подготовить 301;
5. проверить title/description;
6. проверить H1-H3;
7. проверить canonical;
8. проверить sitemap Rank Math;
9. проверить robots;
10. проверить Schema.org отдельным проходом.

Старый сайт содержит больше сущностей, чем шесть подготовленных HTML-макетов, поэтому перенос нельзя считать простым переносом этих шести страниц.

Формат таблицы миграции:

`old URL → new URL → type → status → redirect`

## Правила разработки

1. Не ломать существующую BEM-разметку.
2. Не менять логику CSS/JS без необходимости.
3. Повторяющийся контент — CPT/Repeater, а не копипаст.
4. Глобальные данные хранятся один раз.
5. Логику темы разделять по `functions/*.php`.
6. ACF JSON всегда коммитить.
7. URL старого сайта считать SEO-контрактом до утверждения карты миграции.
8. Не ставить плагин, если задача проще и надежнее решается кодом.
9. После каждой крупной страницы сверять desktop и mobile с исходной версткой/Figma.
10. Schema.org делать после стабилизации структуры сущностей.

## Автоматическое наполнение

Проект должен разворачиваться уже наполненным по утверждённой верстке/макету.

Правила:
- без ручной кнопки импорта;
- при первом заходе в админку тема автоматически создаёт базовые страницы и записи;
- исходные тексты, изображения и ссылки берутся из утверждённой статической верстки в `html/` и `assets/`;
- пути к изображениям переводятся на ассеты темы автоматически;
- главная назначается автоматически;
- меню создаются и назначаются автоматически;
- глобальные ACF-настройки заполняются значениями из макета только если поле ещё пустое;
- последующие ручные изменения глобальных настроек не должны перетираться обновлением темы;
- для страниц из макета сохраняется исходная BEM-разметка без `wpautop`;
- визуальный результат после установки темы должен совпадать с утверждённым макетом без отдельного этапа ручного наполнения.

Текущие автоматические источники:
- `html/index.html` → Главная;
